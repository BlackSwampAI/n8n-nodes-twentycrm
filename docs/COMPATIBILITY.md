# Compatibility and qualification

The project has live-qualified a pinned self-hosted Twenty v2.9.0 development matrix and has fixture-based Metadata GraphQL compatibility coverage for Twenty v2.35.0, but not a broad operational version matrix. The package is available through n8n's verified community-node discovery; that distribution status is separate from the runtime matrix.

The local integration harness pins Twenty v2.9.0 by tag and verified image digest, with explicitly versioned PostgreSQL and Redis images rather than `latest`. CI covers the Node.js 22.22.0 floor and Node.js 24. Twenty Cloud has not been live-qualified, and neither n8n verification nor compatibility with every n8n/Twenty release is claimed.

The credential accepts absolute HTTP or HTTPS root URLs, allowing HTTPS Twenty Cloud URLs and HTTP or HTTPS self-hosted installations. URL normalization, authenticated request construction, safe error normalization, bounded retry policy, and the read-only Core GraphQL credential probe are unit-tested with mocks and exercised against the pinned self-hosted stack. Twenty error payloads and `Retry-After` behavior are treated defensively rather than as a stable vendor-specific contract.

n8n verified-node distribution is established, but it must not be presented as evidence of broader Twenty API, deployment, or runtime compatibility. Those claims require the relevant automated and hands-on checks.

Twenty 2.46 caps default Core REST root-field selection at 200 eligible fields. The released parser accepts a comma-separated `fields` query, trims and deduplicates names, validates them through the selection builder, and always includes `id`; `depth` accepts only 0 or 1. Get and Get Many therefore expose optional root Fields and Depth controls. Absent or blank Fields omits `fields`; absent Depth omits `depth`; untouched options preserve the previous request shape. Compound fields such as name, emails, and address are selected as whole root fields; nested, dotted, wildcard, compound-child, and GraphQL selections are not accepted. One-to-many root fields require Depth 1. More than 200 explicit names are serialized because the upstream constant governs default selection, but explicit selection remains subject to field permissions, relation/query complexity, and request URL or proxy length limits. Users of wide objects should request only needed fields or partition reads and join by `id`. Servers before 2.46 may ignore unknown selection parameters, so projection is not guaranteed there. See the [v2.46 release](https://github.com/twentyhq/twenty/releases/tag/twenty/v2.46.0), [field-selection change #27195](https://github.com/twentyhq/twenty/pull/27195), [fields parser](https://github.com/twentyhq/twenty/blob/twenty/v2.46.0/packages/twenty-server/src/engine/api/rest/input-request-parsers/fields-parser-utils/parse-fields-rest-request.util.ts), [default cap](https://github.com/twentyhq/twenty/blob/twenty/v2.46.0/packages/twenty-server/src/engine/api/rest/input-request-parsers/constants/rest-api-default-max-fields.constant.ts), and [selection builder](https://github.com/twentyhq/twenty/blob/twenty/v2.46.0/packages/twenty-server/src/engine/api/common/common-select-fields/common-select-fields-builder.ts).

Twenty 2.47 rejects generic REST Create, Update, and Delete for workflow and workflowVersion objects. Before one of these generic writes, the node lazily reads the public `/client-config` version once per execution/service and blocks stable versions 2.47 or newer with migration guidance. Reads, fixed resources, and unrelated objects do not depend on the probe. A missing, failed, malformed, ambiguous, or prerelease version is treated as unknown and allowed to preserve older installations; if Twenty then returns 403/405, the error explains both permissions and the 2.47 restriction. Existing metadata read-only and creatable restrictions still run first. See the [v2.47 release](https://github.com/twentyhq/twenty/releases/tag/twenty/v2.47.0), [#27855](https://github.com/twentyhq/twenty/pull/27855), the tag-pinned [client-config controller](https://github.com/twentyhq/twenty/blob/twenty/v2.47.0/packages/twenty-server/src/engine/core-modules/client-config/client-config.controller.ts), and [client-config service](https://github.com/twentyhq/twenty/blob/twenty/v2.47.0/packages/twenty-server/src/engine/core-modules/client-config/services/client-config.service.ts).

Twenty 2.46 also enforces webhook delivery admission for every workspace. The default is 60 calls per 60,000 ms, shared across endpoints/subscriptions. Excess events are sliced out before jobs are enqueued, logged as dropped, and counted by the `JobWebhookCallThrottled` metric; node retries cannot recover them. Self-hosted defaults are controlled by `WEBHOOK_CALL_RATE_LIMITING_LIMIT` and `WEBHOOK_CALL_RATE_LIMITING_TTL_IN_MS`, with a workspace usage override supported upstream. Filter subscriptions in Twenty and use scheduled, watermark-based reconciliation when loss matters. See [#27278](https://github.com/twentyhq/twenty/pull/27278), the [v2.46 rate-limit service](https://github.com/twentyhq/twenty/blob/twenty/v2.46.0/packages/twenty-server/src/engine/metadata-modules/webhook/jobs/webhook-rate-limit.service.ts), [configuration defaults](https://github.com/twentyhq/twenty/blob/twenty/v2.46.0/packages/twenty-server/src/engine/core-modules/twenty-config/config-variables.ts), and [workspace usage-limit definitions](https://github.com/twentyhq/twenty/blob/twenty/v2.46.0/packages/twenty-server/src/engine/core-modules/usage-limit/constants/usage-limit-definitions.constant.ts). Pull request #27278 made webhook rate enforcement unconditional.

Metadata discovery prefers the v2.35 `isUIEditable`/`isUICreatable` shape and safely falls back to the legacy v2.9 `isUIReadOnly`/`isCustom` shape when the modern query is rejected. Because v2.35 no longer exposes a direct object or field `isCustom` flag, that classification is retained when the legacy API supplies it and otherwise remains unknown; the node does not infer it from unrelated flags. Fixed Company, Person, Opportunity, Task, and Note REST routes use shared explicit descriptors, so their reads and JSON-input CRUD are independent of Metadata GraphQL. Generic Record, Schema Object, selectors, and field mapping still require metadata access.

The v2.35 compatibility path must still be live-qualified against an isolated pinned v2.35 stack and through an HTTPS reverse proxy before expanding the live support claim. Do not point mutation qualification at a production workspace. The retained v2.9 harness and volumes must not be upgraded in place.

The v2.9.0 harness qualifies authenticated routing to Core GraphQL and Metadata GraphQL after a user creates a local API key through Twenty's supported UI. Its opt-in discovery check runs the compiled canonical object-metadata query and normalizer. Core REST qualification exercises generic Record reads plus disposable Company, Person, Opportunity, Task, and Note lifecycles with guaranteed cleanup and absence checks.

The expanded local matrix also creates a uniquely owned custom object and writable scalar field through the public v2.9 Metadata GraphQL API, rediscovers them through compiled metadata normalization, and exercises generic Record Create/Get/Get Many/Update/Delete. Cleanup deletes the owned record, field, and object and verifies absence. The mutation path is restricted to a loopback Twenty URL and prints no workspace identifiers, object or field API names, labels, record or schema values, payloads, or counts. This does not establish a broad operational support matrix. See [Local Twenty integration harness](LOCAL_TWENTY.md).

Native webhook qualification uses a deterministic Linux Docker host-gateway alias on the pinned v2.9 worker and Twenty's supported outbound safe-mode configuration. A signed native Twenty-to-n8n production delivery has passed on this matrix. Registration remains manual, and no private management API is used. See the [UI qualification checklist](QUALIFICATION.md) for the bounded editor inspection.

The current public webhook page describes an `event`/`data`/`timestamp` body. In contrast, current official sender source at commit `ee6a5c37cd9dc420934c02cf32256234f7e96d01` still emits the `eventName`/`objectMetadata`/`workspaceId`/`webhookId`/`eventDate`/`record` envelope used by the pinned live fixture and signs the serialized payload without its secret using a 13-digit millisecond timestamp. The trigger intentionally follows the observed/current implementation; no current-version live delivery is claimed solely from source inspection.
