# Architecture

Twenty is treated as a dynamic workspace-schema platform rather than a fixed set of CRM resources.

The integration separates four API surfaces derived from one normalized root URL: core REST (`/rest`), core GraphQL (`/graphql`), metadata REST (`/rest/metadata`), and metadata GraphQL (`/metadata`). Root normalization supports Twenty Cloud and self-hosted reverse-proxy path prefixes without scattering endpoint construction. Record operations use REST; schema discovery uses Metadata GraphQL.

One shared object metadata service now fetches the canonical paged Metadata GraphQL object connection for execution and editor selectors. It protects against missing/repeated cursors and excessive pages, then deterministically normalizes object and field identity, labels, lifecycle and access flags, defaults, options/settings, and relation endpoints. Unknown future field-type strings and unfamiliar option/settings values remain opaque data rather than invalidating the schema. Saved workflows use stable singular API names rather than display labels.

The node exposes read-only `Schema Object` operations and generic Record `Create`, `Get`, `Get Many`, `Update`, and `Delete`. Friendly Company, Person, Opportunity, Task, and Note resources are thin metadata-aware wrappers over the same Record service rather than separate clients. Each derives a stable API name, exposes a small preferred set of discovered writable fields in an initially visible Common Fields mapper, and leaves remaining active writable fields (including custom fields) in Additional Fields. Both mapper value sets are validated together and reconstructed once so compound parents remain intact. Metadata-proven direct relation IDs are exposed only for explicitly configured source/field/target triples; fixed resources omit raw child and morph relations. Missing preferred metadata is skipped, and generic Record retains its raw relation/JSON escape hatches.

Schema and generic Record resources reuse the editor selector of active workspace objects, excluding inactive/system/remote objects and sorting by singular label. Generic Record operations resolve the singular API name through metadata and use the metadata-derived plural Core REST route. Fixed resources instead share explicit validated singular/plural descriptors, keeping fixed REST reads and JSON-input CRUD independent of Metadata GraphQL; their Field Mapping mode remains metadata-driven. Metadata discovery prefers the v2.35 editable/creatable flags and falls back to the legacy v2.9 read-only/custom shape without guessing a removed custom classification. List reads parse Twenty's `data.<plural>[]` envelope, cap each API page at 200 records, preserve documented raw `filter` and `order_by` strings across `starting_after` cursor pages, and guard missing/repeated cursors and excessive traversal. Create/Update default to n8n's native resource mapper, using stable field API names and a pure adapter that reconstructs bounded compound values; unknown types remain available as raw JSON. The prior JSON-object path remains an explicit advanced input mode. POST, PATCH, and DELETE never opt into transport retries. Delete ignores the response body and returns a deterministic local confirmation. Schema writes remain deferred.

The shared layer contains type-only service contracts, a pure dependency-free URL helper, and one authenticated request helper for execution and load-option contexts. The helper retrieves the `twentyApi` credential, derives the selected API surface, and delegates Bearer authentication to n8n's `httpRequestWithAuthentication`. It normalizes variable HTTP, network, and GraphQL failures into actionable n8n-native errors built only from safe synthetic details; response bodies, headers, GraphQL messages and paths, credentials, and private values are not retained.

Transport retries are conservative and deterministic: automatic retries apply only to GET and HEAD, callers must explicitly mark another request as safe/idempotent, and callers can disable retries. Only rate limits, temporary gateway/service failures, timeouts, connection resets, and temporary DNS failures are retried, for at most three total attempts. `Retry-After` delay-seconds and HTTP-dates are honored up to 60 seconds; otherwise the two retries wait 250 ms and 500 ms. GraphQL errors and permanent request, authentication, permission, conflict, URL, DNS, connection, and TLS failures are not retried.

Credential validation is a node-level custom test that sends only `query CredentialTest { __typename }` to Core GraphQL. It validates routing and authentication without reading or mutating workspace records, reusing safe error classification without retrying. Metadata discovery has no cache.

The Twenty CRM Trigger is manually registered because no stable public webhook-management API is used. The user enters a strong shared secret in Twenty's webhook form even though Twenty labels it optional, then saves the same secret in the dedicated password-masked credential. Unsigned mode is not supported. Intake verifies the sender contract (`timestamp:rawBody`, HMAC-SHA256 hex) against n8n's raw request bytes with constant-time comparison before parsing or filtering. Current sender source at commit `ee6a5c37…` constructs `eventName`, `objectMetadata`, `workspaceId`, `webhookId`, `eventDate`, and `record`, removes the secret, sets a 13-digit `Date.now()` header, and signs `timestamp:JSON.stringify(payloadWithoutSecret)`. That implementation differs from the public docs' `event`/`data`/`timestamp` example but matches both the pinned v2.9 delivery and this parser. Millisecond timestamps must be within five minutes in either direction. The trigger then filters `eventName` and `objectMetadata.nameSingular`, supporting active standard/custom objects and an All Objects choice. Nonce persistence is intentionally not attempted in node-local memory because n8n executions may span workers; the bounded signed timestamp is the replay control for v0.1.

The opt-in local integration harness mirrors Twenty v2.9.0's server, worker, PostgreSQL, and Redis Compose topology with immutable or explicit image versions. Its live qualification probes both GraphQL surfaces, all five fixed-resource lifecycles, generic Record reads, a disposable custom schema plus generic CRUD, and native signed webhook delivery. Schema mutation is restricted to loopback and requires Data Model permission. Default tests inspect the harness offline; Docker startup and authenticated probes are never implicit CI steps.
